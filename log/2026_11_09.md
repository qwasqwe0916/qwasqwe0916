### ERD 설계 (`docs/erd.md`)
* 테이블 8개 설계: users, categories, skills, user_skills, posts, post_skills, comments, applications
* 관계 정리: 1:N 관계 4개, M:N 관계 3개(user_skills, post_skills, applications)
* Mermaid로 ERD 다이어그램 작성 (GitHub에서 그림으로 확인)
* 테이블별 컬럼, 타입, 제약조건 및 설계 결정 사항 정리

### 이해한 내용
* 다대다(M:N) 관계는 양쪽 모두 여러 개를 가질 수 있는 관계이며, 중간 테이블로 분해하여 1:N 두 개로 표현한다
* `post_skills`의 필수/선택, `applications`의 상태·메시지처럼 **조합에 붙는 정보**는 중간 테이블에 둔다
* PK(기본 키), FK(외래 키), UK(유일 키)의 의미와 복합 기본 키
* 기술 이름은 `skills`에 한 번만 저장하고, 다른 테이블은 번호(`skill_id`)로 참조한 뒤 JOIN으로 조회한다

### 정규화 검토 (`docs/normalization.md`)
* 정규화 전 테이블의 문제점(삽입·갱신·삭제 이상) 정리
* 1NF: 여러 값을 가지는 속성(기술 스택, 지원자)을 별도 테이블로 분리
* 2NF: 복합 키 테이블(`user_skills`, `post_skills`, `applications`)의 부분 종속 없음 확인
* 3NF: 작성자 이름, 카테고리 이름 등 이행 종속을 FK 참조로 제거
* 지원자 수, 수락 인원 등은 저장하지 않고 조회 시 계산

### DB 구축 (`db/`)
* `schema.sql`: 테이블 8개 생성 (PK, FK, UNIQUE, CHECK, ENUM, ON DELETE CASCADE)
* `seed.sql`: 카테고리 3개, 기술 스택 임시 목록 21개
* `sample.sql`: 개발·테스트용 샘플 데이터 (회원 3명, 게시글 3개, 댓글, 지원 내역)
* 로컬 MySQL에서 실행 및 조회 확인 완료
* 제약조건 동작 확인: 중복 지원, 모집 인원 0명, 없는 회원 참조, 기술 스택 중복(대소문자), 잘못된 상태값, 사용 중인 기술 삭제가 모두 차단됨. 게시글 삭제 시 하위 데이터 함께 삭제됨
