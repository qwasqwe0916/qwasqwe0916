# 📋 요구사항 명세 (Requirements)

* 대상: Campus Teammate Matcher (교내 팀원 매칭 플랫폼)
* 작성일: 2026-11-09
* 각 요구사항의 **구현 위치**는 해당 규칙을 어디에서 보장하는지를 나타낸다.
  * **DB:** MySQL 제약조건(PK, FK, UNIQUE, NOT NULL, ENUM, CHECK)으로 보장
  * **서버:** 백엔드에서 로그인 토큰과 권한을 검사하여 보장
  * **SQL:** 조회 쿼리(JOIN 등)로 구현
  * **Supabase:** Supabase Auth 설정으로 보장

---

## 1. 사용자 유형

| 유형 | 설명 |
|---|---|
| 비회원 | 로그인하지 않은 방문자. 게시글과 프로필 조회만 가능 |
| 회원 | 교내 이메일 인증을 마친 사용자. 글 작성, 댓글, 지원 가능 |
| 작성자 | 특정 게시글을 작성한 회원. 해당 글의 수정, 삭제, 지원자 관리 가능 |
| 지원자 | 특정 게시글에 지원한 회원. 본인 지원 내역 조회 및 취소 가능 |

---

## 2. 기능 요구사항

### (1) 회원
| 번호 | 요구사항 | 구현 위치 |
|---|---|---|
| R1 | 교내 이메일(`@seoultech.ac.kr`)로만 가입할 수 있다 (타 대학 이메일은 가입 불가) | Supabase, 서버 |
| R2 | 첫 로그인 시 이름(필수, 실명), 학과(선택), GitHub URL(선택)을 입력한다. 이름은 중복을 허용한다 | DB, 서버 |
| R3 | 보유 기술 스택을 여러 개 등록할 수 있다. 기술 스택은 **미리 정해진 목록에서만** 선택하며, 사용자가 새 항목을 추가할 수 없다 | DB (`user_skills`, `skills`) |
| R4 | 본인 프로필만 수정할 수 있다 | 서버 |

### (2) 게시글
| 번호 | 요구사항 | 구현 위치 |
|---|---|---|
| R5 | 회원만 글을 작성할 수 있으며, 카테고리를 반드시 하나 선택한다 | DB (FK, NOT NULL), 서버 |
| R6 | 게시글마다 필요한 기술 스택을 **필수/선택**으로 구분하여 여러 개 지정할 수 있다 | DB (`post_skills`) |
| R7 | 모집 인원(1명 이상)과 마감일을 지정할 수 있다 | DB (CHECK) |
| R8 | 게시글은 **모집중 / 모집완료** 상태를 가지며, 작성자가 상태를 변경할 수 있다 | DB (ENUM), 서버 |
| R9 | 작성자만 게시글을 수정하거나 삭제할 수 있다 | 서버 |
| R10 | 게시글 삭제 시 해당 글의 댓글, 지원 내역, 기술 태그도 함께 삭제된다 | DB (`ON DELETE CASCADE`) |
| R11 | 비회원도 게시글 목록과 상세 내용을 조회할 수 있다 | 서버 |
| R12 | 카테고리와 기술 스택으로 게시글 목록을 필터링할 수 있다 | SQL (JOIN) |

### (3) 댓글
| 번호 | 요구사항 | 구현 위치 |
|---|---|---|
| R13 | 회원만 댓글을 작성할 수 있다 | 서버 |
| R14 | 본인이 작성한 댓글만 삭제할 수 있다 (수정 기능은 제공하지 않는다) | 서버 |

### (4) 프로필
| 번호 | 요구사항 | 구현 위치 |
|---|---|---|
| R15 | 누구나 게시글 작성자 및 댓글 작성자의 프로필(이름, 학과, 기술 스택, GitHub URL)을 조회할 수 있다 | SQL (JOIN) |

### (5) 지원
| 번호 | 요구사항 | 구현 위치 |
|---|---|---|
| R16 | 회원은 **모집중**인 게시글에만 지원할 수 있다 | 서버 |
| R17 | 한 사용자는 같은 게시글에 **한 번만** 지원할 수 있다 | DB (UNIQUE) |
| R18 | 본인이 작성한 게시글에는 지원할 수 없다 | 서버 |
| R19 | 지원 상태는 **대기 / 수락 / 거절** 중 하나이며, 지원 시 **대기**로 시작한다 | DB (ENUM, DEFAULT) |
| R20 | 작성자만 해당 글의 지원자 목록을 조회하고 수락 또는 거절할 수 있다. 지원자 목록에는 지원자의 이름, GitHub URL, **보유 기술 스택 전체**를 함께 표시한다 | 서버, SQL (JOIN) |
| R21 | 지원자는 본인의 지원 내역과 상태를 조회할 수 있다 | SQL |
| R22 | 지원자는 **대기** 상태일 때만 지원을 취소할 수 있다 (취소 시 지원 내역 삭제) | 서버 |

## 3. 비기능 요구사항

| 번호 | 요구사항 |
|---|---|
| N1 | 브라우저는 MySQL에 직접 접근하지 않으며, 모든 데이터 요청은 백엔드 서버를 거친다 |
| N2 | 서버는 보호된 요청마다 Supabase 로그인 토큰(JWT)을 검증하며, 클라이언트가 보낸 사용자 ID를 신뢰하지 않는다 |
| N3 | DB 접속 정보와 키는 `.env`에만 보관하고 저장소에 올리지 않는다 |
| N4 | 한글 데이터 저장을 위해 DB 문자셋은 `utf8mb4`를 사용한다 |

## 4. 추가 검토 기능 (일정 여유 시 구현)

| 항목 | 내용 |
|---|---|
| 필수 기술 보유 현황 표시 | 지원자 목록에서 게시글의 필수 기술 대비 지원자의 보유 개수를 표시 (예: "필수 기술 2개 중 2개 보유"). `post_skills`와 `user_skills`를 비교하여 조회 |

## 5. 제외 범위 (이번 프로젝트에서 구현하지 않음)

| 항목 | 사유 |
|---|---|
| 댓글 수정 | 작성과 삭제만으로 충분하며 일정 절약 |
| 회원 탈퇴 | 작성 글, 지원 내역 처리가 복잡해지며 과제 범위를 벗어남 |
| 수락된 지원의 취소 | 작성자의 팀 구성에 혼란을 줄 수 있음 |
| 기술 스택 분야 분류 (프론트엔드, 백엔드 등) | 테이블과 화면이 복잡해짐. 목록이 길어질 경우 추후 검토 |
| 사용자의 기술 스택 직접 추가 | 표기 불일치(`React`, `react`, `리액트`)로 필터 기능이 손상됨 |
